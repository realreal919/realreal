# 誠真之友 v2：現況對照與開發計畫

對照對象：《誠真之友：會員制度完整開發規格 v2》
盤點日期：2026-10-07（盤的是正式環境的資料與 `main` 上的程式碼）

## 0. 最重要的一件事：公益存款已經存在，而且就是「點數」

規格把 `charity_ledger` 寫成要新建的表。實際上**這個帳本已經在跑了**，叫 `points_ledger`，前台的字樣就是「公益點數」「本次公益存款」，1 點 = NT$1。

| 規格想要的 | 現況 |
|---|---|
| `charity_ledger` 流水帳 | `points_ledger`（id, user_id, delta, source, source_ref_id, note, expires_at, actor_id, created_at），314 筆 |
| 可折抵消費 | 已可折抵，結帳頁顯示「✨ 點數折抵」 |
| 單筆上限 20% | **已經生效**（2026-10-04 上線，`MAX_REDEEM_PCT = 20`） |
| 消費回饋進帳本 | 已進帳（source = `earn`，234 筆 / 7,266 點） |
| 餘額 | 全站未使用餘額 8,849 點 |

`user_profiles.charity_savings` 那個欄位在程式碼裡被註記為 **legacy display mirror**，是舊的顯示用鏡像，不是真正的帳本。

**建議：不要新建 `charity_ledger`，改為擴充 `points_ledger`。** 另開新表會造成兩套餘額、兩套折抵邏輯，而舊的那套正在處理真實金額。

需要補的只有三件事：

1. `source` 目前是自由字串，現有值為 `earn` / `manual_adjust` / `refund` / `redeem`。規格要 `rebate` / `referral` / `birthday`。做法：新來源直接用新值，`earn` 視為 `rebate` 的歷史別名，不回頭改資料。
2. 沒有 `status` 欄位。現行是 delta 正負相抵，沒有「捐出」這個狀態。**「捐出」是全新概念**，要新增 `status` 與 `donated_at`。
3. **現有 314 筆的 `expires_at` 全部是空的**，等於目前所有公益存款都不會過期。規格要生日存款 90 天、推薦 180 天效期 —— 效期機制要從零開始做（含到期前 30 天提醒、到期自動轉公益）。

## 2. 直接衝突的地方（需要你決定）

### 2.1 回饋率要從 2 / 2.5 / 3 改成 3 / 3 / 3
現行 `membership_tiers.rebate_rate` 是 初心 2%、知心 2.5%、同心 3%。規格的 `rebate_rate_by_tier` 三層都是 3。

這等於**幫初心加碼 50%、知心加碼 20%**，而初心佔了 238 / 261 位會員。以九月的營收規模估，公益存款支出會從約 3,400 元／月增加到約 5,100 元／月。

同時這會讓層級失去一個主要誘因 —— 三層的回饋率一樣之後，升等的實質差別只剩生日禮金（50/100/150）與「不定期專屬優惠」。

**要確認：真的要統一 3%，還是維持現行階梯？**

### 2.2 升級規則整個換掉
| | 現行 | 規格 v2 |
|---|---|---|
| 初心 → 知心 | 累計消費 ≥ 3,500 | **第二張完成訂單**（不同日、未退貨） |
| 知心 → 同心 | 累計消費 ≥ 12,000 | 12 個月內互動點數 ≥ 15 |
| 知心效期 | 12 個月 | 12 個月（相同） |
| 同心效期 | **36 個月** | **24 個月** |
| 到期處理 | 期間消費達 requalify 就續等，否則**自動降級** | **不自動降級**，延長一期並通知 |

影響評估：改成「第二張訂單即升知心」之後，**157 位單次客只要再買一次就全部變成知心**。目前知心只有 22 位，上線後可能很快變成 150+ 位。如果回饋率同時統一成 3%，兩件事疊加的成本要一起看。

既有的 22 位知心、1 位同心是用舊規則升的，規格說沿用原效期保留 —— 這點沒問題，照做。

**要確認：同心效期 36 → 24 個月，現有那位同心（效期到 2029-08-26）是否沿用舊效期？** 規格的「舊會員過渡」寫沿用，我會照這個做。

### 2.3 「捐出」是不可逆的，而且規格沒說由誰按
規格寫「會員對每筆可用餘額可選：折抵消費，或捐出（隨時可選、無條件、不可反悔）」。

現行會員中心沒有這個功能，要新做。需要確認的是**捐出之後的錢流**：帳本上標成 `donated` 之後，實際的捐款是年度彙總手動匯出（規格 5.5），所以會員按下「捐出」的當下不會有任何對外動作。這點要在介面上講清楚，不然會員會以為立刻捐了。

### 2.4 到貨日幾乎一定取不到（規格 7.5 的答案是「取不到」）
規格說「若系統取不到實際到貨日，以出貨日 + 2 天估算」，把它當成例外。

**實際上這會是常態。** 今天剛確認：7-11 出貨是用交貨便批次上傳，不走站上的綠界物流整合，所以**綠界的取貨回報永遠不會回來**（23 筆 COD 訂單因此卡在待付款將近一個月，是第三次發生）。`orders` 目前也沒有 `delivered_at` 欄位。

**結論：回購提醒實務上一律是「出貨日 + 2 天 + N」。** 建議直接把它定為正式算法，而不是備案 —— 否則會寫出一段永遠不會執行的分支，還讓人誤以為提醒天數是從真實到貨日算的。

### 2.5 設定表要改兩個地方才會生效
規格列了 20 個設定值。現行的設定是 **AES-256-GCM 加密存在 `app_settings.value_enc`**，金鑰只在 Railway 環境變數，**不能直接寫資料庫**，而且 `apps/api/src/lib/settings.ts` 裡有一份白名單，沒列進去的 key 讀不到也存不了。

所以每個新設定都要：(1) 加進 `settings.ts` 白名單；(2) 在後台設定頁加欄位。這是純工，但要算進工時。

## 4. 分期建議

**階段 0｜地基（不改變任何對會員可見的行為）**
設定白名單與後台欄位、`points_ledger` 的 `status` / `donated_at`、`orders.delivered_at` / `is_first_order`、`user_profiles` 四個新欄位。
→ 可以先做，沒有爭議。

**階段 1｜首購與回購（商業價值最高）**
計量勺贈品、`member_coupons`、回購券、回購提醒排程、召回名單匯出。
→ 157 位單次客是現在最大的機會。

**階段 2｜公益存款完整化**
效期機制、到期提醒、會員「捐出」、年度捐出報表、`donation_batches`。

**階段 3｜層級制度換軌**
升級規則改版、到期不降級、建議名單、層級檢視頁。
→ 放在回饋率決定之後，因為兩者的成本是連動的。

**階段 4｜推薦**
推薦碼、歸屬、獎勵佇列、確認頁。

**階段 5｜互動點數**
`member_interactions`、建議邀請名單。

## 7. 2026-10-07 店主追加的三項定調（已套用）

### 7.1 公益優先、折抵是例外
- **取消「捐出」按鈕。** 文案不再把捐出寫成一個選項 —— 公益存款預設就是用於公益，折抵才是例外。
- **所有來源都不設效期。** 回饋、推薦、生日的存款都持續累積，沒用掉不會消失。
- 因此整套效期機制不做了：沒有到期掃描、沒有到期前 30 天提醒、沒有 `expired_donated` 狀態。
- 年度捐出改成「把累積下來還沒被折抵掉的餘額整批結算」，不是逐筆要會員決定。帳本狀態因此簡化為 `available` / `redeemed` / `reversed` / `settled`。

這讓原本的階段 2（公益存款效期與捐出）縮小到只剩年度結算報表。

### 7.2 計量勺改看「有沒有拿過」，不看是不是首購
原規格寫「首購附勺」。店主補充：**還沒拿過勺的會員，回購時也要送**。

所以條件是 `received_scoop = false` + 訂單折前金額達門檻，與「是不是第一張訂單」無關。

**要注意的量：現有 261 位會員全部是 `false`**，等於每個人下一張達門檻的訂單都會附一支勺。以有購買紀錄的 192 位估算，這是一次性約 192 支的成本。

### 7.3 升知心的第二張訂單要滿 $300（折前）
原規格只寫「第二張完成訂單」。加上 $300 門檻之後，157 位單次客不會因為補一筆小額訂單就全部升等，成本比原案可控。
